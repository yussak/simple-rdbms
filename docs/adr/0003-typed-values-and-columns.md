# 0003. 型付きの値と列定義

- ステータス: 採用
- 日付: 2026-10-22

## コンテキスト

CREATE の AST は列名と型名を持つが、実行器は列名だけを保存していた。
行データと SELECT の結果も文字列のみのため、整数の `1` と文字列の `"1"` を区別できなかった。
INSERT の実装に先立ち、列の型を保持し、値と検索結果でも整数・文字列を区別する。

## 決定

- 共通の `value` パッケージに `Type` と `Value` を置く。
- `Type` は `TypeInvalid` / `TypeInt` / `TypeText` とし、ゼロ値は無効な型とする。
- `Value` は型を示す `Type` と、整数の `Int int64`、文字列の `Text string` を持つ。型に対応したフィールドを使用する。
- `engine.Column` は列名と型を一組で持ち、`Table.Columns` は `[]Column` とする。
- パーサは型名文字列を持つ AST を返し、CREATE 実行器が内部型へ変換する。未対応の型はエラーとし、全列の変換後にテーブルを登録する。
- 行データと SELECT の結果は `[][]value.Value` とする。SELECT の結果の列名は `[]string` とする。

## 検討した代替案

- 列名と型を別々のスライスにする案は、長さと順序の対応を管理する必要があるため採らない。
- パーサの列定義をそのまま保存する案は、テーブルの構造が AST の表現に依存するため採らない。
- AST の段階で内部型へ変換する案も可能だが、今回はパーサを維持して実行器の変更に絞る。
- 値を `any` や型ごとの interface で表す案は、現段階では構造と処理を追いやすい共通の構造体を優先して採らない。

## 結果

列の順序と型、および値の型がメモリ上で保持される。
今後 INSERT を実装する際は、列定義と入力値の型を照合してから保存できる。
`Value` のフィールドは公開しており、不整合な値の構築を型定義だけでは防がない。SQL による挿入時の検証は INSERT の実装で行う。
