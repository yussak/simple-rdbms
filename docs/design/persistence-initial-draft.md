# ファイル永続化の初期草案

この文書は検討の履歴として残す。単一DBファイル案を含むため、現在の設計は[永続化の設計](persistence.md)を参照する。

状態: 設計中。一般的な仕組みと本プロジェクトへの設計案をまとめ、文書への質問・検討を通じて具体化する。

## 1. 目的と進め方

自作RDBMSのテーブル定義と行データをファイルへ保存し、DBを開き直しても利用できるようにする。
性能よりも仕組みの理解と読みやすさを優先し、小さい単位で実装・検証する。

設計は次の順で進める。

1. 全体設計をこの文書にまとめ、目的、ファイル構造、部品の責務、処理のつながりを説明する。
2. 読んで疑問が生じた箇所を確認し、説明を文書へ補足する。判断に必要な説明をしたうえで、要件や実装範囲に関わる選択を相談する。
3. 理解・確認した内容を反映し、未決事項と区別する。
4. 複雑な部分の具体的な仕様は詳細設計書へ分け、重要な判断と理由はADRに記録する。
5. 実装に必要な設計が整理できた部分から、テストと実装を一つずつ進める。

一般的な方式は理由とともに推奨する。設計の選択に必要な説明をする前に、方式の選択を求めない。
説明用の数値・形式と、実装仕様として確定した内容は区別する。

この全体設計では、何をどの部品が扱い、SQLの実行からファイルの読み書きまでどうつながるかを記述する。
ページ内部の正確なバイト配置、値の変換規則、具体的なGoの構造体・関数定義は詳細設計で扱う。

## 2. 確認済みの要件・方針

- DBを閉じて開き直しても、テーブル名、列名、列の順序と型、行データが残る。
- CREATE・INSERT・DELETEの結果を保存し、再度SELECTで確認できる。
- 更新文の成功を返す時点で、変更が保存済みであることを要求する。終了時だけの一括保存にはしない。
- 今回の基本的な完成条件は正常な終了・再オープンとする。書き込み途中のクラッシュからの復旧は後続のWALの段階で扱う。
- 既存ロードマップに沿って、ページ単位のファイル永続化を進める。
- 性能を理想形に近づけるための最適化を先回りして追加しない。

ページ方式の実装順序は [ADR 0001](../adr/0001-phase-implementation-order.md) に記録されている。
今回新たに必要になる判断は、説明・検討を経てからADRに残す。

## 3. 現状と保存対象

現在は `engine.Database.tables` がテーブルを管理し、`engine.Table` が列定義と全行をメモリ上に保持する。
`engine.Execute` がCREATE・INSERT・SELECT・DELETEを実行する。ファイルへの保存は未実装。

| 保存対象 | 例 |
| --- | --- |
| テーブル名 | `users` |
| 列の順序・名前・型 | `id INT, name TEXT` |
| 行データ | `(1, '田中')` |

保存する情報を解釈するため、形式のバージョンやページ・行の位置などの管理情報も必要になる。
管理情報の具体的な項目は今後設計する。

## 4. ファイルとページの意味

DBファイルは、本プログラムが自分たちで定めた形式で読み書きするバイナリファイルである。
テーブル定義や行をバイト列として格納する。

ページは、そのファイル内の固定長の領域である。ページごとにファイルを分けるわけではない。
ページ番号とページサイズから、ファイル内の読み書き位置を計算する。

例えばページサイズが4096バイト、番号が0始まりなら、ページ2の開始位置は8192バイトとなる。
4096バイトという値は現時点では説明用の例であり、具体的なサイズは未確定。

ページ単位にすることで、読み書きと保存領域の管理の単位をそろえられる。
必要な部分だけ読み書きでき、将来B+木をページに保存するときにも使える。
WHEREに合うページが自動的に特定できるわけではなく、インデックスがない検索は基本的に全行走査する。

### ファイル全体の構造案

1つのDBファイルに、役割の異なる3種類の情報を保存する構成を提案する。

```text
DBファイル
├ 管理情報（ファイルヘッダー）
│  └ ファイルの識別子、形式のバージョン、ページサイズ、カタログの場所
├ カタログ
│  └ テーブル名、順序付きの列定義、データページの場所
└ データページ
   └ 行を変換したバイト列と、ページ内の行の位置などの管理情報
```

これは情報の論理的な区分であり、3つのファイルや連続した3領域に分けることを意味しない。
実際には同じDBファイルのページへ配置する。具体的な配置は詳細設計で定める。

ファイルヘッダーは、ファイルを開いたときに最初に読む管理情報である。
識別子とバージョンで本プログラムが読める形式かを確認し、カタログの場所を取得する。
この場所からカタログを読み、各テーブルの定義と行データの保存先をたどる。

カタログは、DB自身が使うテーブルの目録である。
例えば `users(id INT, name TEXT)` について、テーブル名、列の順序・名前・型、行を格納したページをたどるための情報を保持する。
列定義が分かることで、読み出した行のバイト列をどの型の値として復元するか判断できる。

データページは実際の行を格納する。
`(1, '田中')` なら整数の1と文字列の「田中」を変換したバイト列を置く。
複数の行を格納するため、どの位置にどの長さの行があるかも管理する必要がある。
1テーブルの行が複数ページに増えたときのたどり方は、詳細設計で定める。

### バイト列の説明例

`users(id INT, name TEXT)` と行 `(1, '田中')` の情報は、例えば次のように表現できる。
これは各情報の変換例であり、ファイル全体の形式やページ上の配置を定めるものではない。

| 情報 | バイト列（16進数） | 説明 |
| --- | --- | --- |
| テーブル名 | `05 75 73 65 72 73` | 名前のバイト長5とUTF-8の `users` |
| 列数 | `02` | 2列 |
| 列名とINT型 | `02 69 64 01` | 名前のバイト長2、`id`、型番号1 |
| 列名とTEXT型 | `04 6E 61 6D 65 02` | 名前のバイト長4、`name`、型番号2 |
| 整数1 | `00 00 00 00 00 00 00 01` | 8バイトの整数 |
| 文字列「田中」 | `00 00 00 06 E7 94 B0 E4 B8 AD` | UTF-8のバイト長6と本文 |

長さのフィールド幅、型番号、整数のバイト順、上限値は、詳細設計で定める。
Goの構造体のメモリをそのまま保存するのではなく、読み書きで共通の変換規則を使う。

## 5. コンポーネント構成案

以下は今後説明・検討する構成案。パッケージ名や公開APIは未確定。

| 部品 | 担当する内容 |
| --- | --- |
| SQL実行器 | テーブル定義に基づく列数・型・条件の検証、WHEREの判定、保存操作の呼び出し、SELECT結果の組み立て |
| テーブル管理 | カタログによるテーブル定義と保存先の管理、行の追加・走査・削除、必要なデータページの選択 |
| 行とページの形式を扱う処理 | 型付きの値とバイト列の相互変換、ページ内の行の位置・長さ・空き領域の管理 |
| ページI/O（Pager） | ページ番号による読み書き、新規ページの確保、ファイルの同期・クローズ。SQLや列の意味は扱わない |

```text
SQLの入力
    ↓
既存のlexer / parser：SQLをASTへ変換
    ↓
実行器：検証・条件判定・結果の組み立て
    ↓
テーブル管理：カタログと行の操作
    ↓ 行・ページの形式を扱う処理でバイト列に変換
Pager：ページ単位のI/O
    ↓
DBファイル
```

読み出しではDBファイルから逆方向に、ページ、行、型付きの値へと復元する。
行の変換処理とページ内の配置処理を別パッケージにするかなど、コード上の分割は詳細設計で決める。
SQL入力用CLIは別の開発項目であり、永続化の検証は実行器を呼ぶテストから行える。

現在の `Table.Rows` をどの段階で置き換えるかは、各責務を説明した後に整理する。
キャッシュやバッファプールの高度な管理は、初期構成に当然必要なものとはしない。

## 6. データフロー案

### DBを開く

既存DBでは、ファイルを開く → ヘッダーの形式を確認する → カタログの場所を取得する → テーブル定義と行データの保存先を参照できる状態にする。
初版で全行をメモリに読み込むことは前提とせず、行が必要になったときにデータページを読む構成を提案する。
カタログをどこまでメモリへ保持するかは未確定。

新規DBではヘッダーと空のカタログを初期化する必要がある。
新規作成と既存DBのオープンをどう指定するかはAPIの詳細設計で決める。
読めない形式や壊れたファイルを、空のDBとして上書きしてはならない。

### CREATE

テーブル名・列定義を検証する → テーブル管理がカタログに定義と保存先の情報を登録する → 変更したページを書き込む → 同期して成功を返す。
同名テーブルを上書きせずエラーにする方針を提案する。これは既存TODOにも記載されている。
空テーブルのデータページをCREATE時に確保するか、最初のINSERTまで遅らせるかは詳細設計で決める。

### INSERT

カタログから列定義を取得する → 実行器が列数と型を検証する → 行をバイト列に変換する → 保存先のページを読み、行を追加する → 変更したページを書き込む → 同期して成功を返す。
保存先に空きがなければ新しいデータページを確保し、そのページを後からたどれるよう管理情報も更新する。
空きページの探し方と、1ページを超える行の扱いは未確定。

### SELECT

カタログから列定義と保存先を取得する → 実行器が選択列とWHERE全体を検証する → データページを走査して各行を値に復元する → WHEREに一致する行の必要な列を結果へ追加する。
例えば `SELECT * FROM users` なら、`users` のデータページをたどり、削除されていない全行を列定義の順序で復元する。
最初はインデックスを使わずフルスキャンする。SELECTでは保存済みのデータを変更しない。

### DELETE

カタログから列定義と保存先を取得する → 実行器がWHERE全体を検証する → データページを走査し、一致する行を削除対象とする → 削除をページに反映する → 書き込み・同期後に成功を返す。
WHEREなしでは全行を削除する。カタログのテーブル定義は保持し、再オープン後もINSERTできる状態にする。
削除済みの印を付けるか、残す行を詰め直すかといった、ページ内での削除表現は詳細設計で決める。

### 保存完了とDBを閉じる処理

更新文では、行データだけでなく、その操作で変更したカタログなどの管理情報も書き込み対象となる。
必要な書き込みとファイルの同期が成功してから、SQLの成功を呼び出し元へ返す。
DBを閉じる際はファイルなどの資源を解放する。更新内容の保存をこの時点まで先送りしない。

同期APIの呼び出し位置やI/O失敗後の扱いは未確定。
同期は更新文の途中で起きるクラッシュからの復旧や、複数ページの更新の原子性を保証するものではない。
既存の入力検証エラーでデータを変更しない性質と、書き込み途中のI/O失敗・クラッシュの扱いを分けて設計する。
失敗時のディスクとメモリの状態について、WALなしで保証できる範囲を明記する必要がある。

## 7. 次に理解・検討するテーマ

1. ページの内部構造: 行の位置と長さをどのように管理するか。
2. 行の形式: INT・TEXTの変換規則とサイズ制限。
3. テーブルの管理: 列定義とデータページをどう関連付けるか（カタログ）。
4. ページI/O: ページの読み書き、確保、保存完了の扱い。
5. 実行器との接続: 既存のメモリ管理からの移行と、各SQLの動作。
6. 異常時の扱い: 不正ファイル、書き込み失敗、未対応形式への対応。

これらの説明・検討を経て、必要な詳細設計と実装手順を具体化する。
スロット方式、削除領域の扱い、ページを超える行、キャッシュ方針などの提案は未確定である。

## 8. 実装・検証の進め方（案）

設計が整理できた部分ごとに、次の小さい単位で進める。各段階の具体的なAPIは未確定。

1. ページの書き込みと、ファイルを開き直した後の読み出し。
2. 型付きの値の変換と、ページ内での行の格納・読み出し。
3. テーブル定義の保存・復元。
4. CREATE → INSERT → SELECTと、再オープン後の結果確認。
5. DELETEと、再オープン後も削除結果・列定義が維持されることの確認。
6. 境界値・失敗時の検証と、既存機能の回帰確認。

DB全体がメモリに残っていることで誤って成功しないよう、復元の検証には新しく開いたDBを使う。
クラッシュ復旧の実装は後続のWALの段階で扱う。
