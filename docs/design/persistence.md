# ファイル永続化の全体設計

状態: 設計中。対話で理解・確認した内容を順に反映する。

## 1. 目的と進め方

自作RDBMSのテーブル定義と行データをファイルへ保存し、DBを開き直しても利用できるようにする。
性能よりも仕組みの理解と読みやすさを優先し、小さい単位で実装・検証する。

設計は次の順で進める。

1. 一つのテーマについて、解決する問題、一般的な仕組み、本プロジェクトへの提案を説明する。
2. 疑問点を確認し、要件や実装範囲に関わる判断を相談する。
3. 理解・確認した内容をこの文書に反映する。
4. 複雑な部分の具体的な仕様は詳細設計書へ分け、重要な判断と理由はADRに記録する。
5. 実装に必要な設計が整理できた部分から、テストと実装を一つずつ進める。

一般的な方式は理由とともに推奨する。設計の選択に必要な説明をする前に、方式の選択を求めない。
説明用の数値・形式と、実装仕様として確定した内容は区別する。

## 2. 確認済みの要件・方針

- DBを閉じて開き直しても、テーブル名、列名、列の順序と型、行データが残る。
- CREATE・INSERT・DELETEの結果を保存し、再度SELECTで確認できる。
- 更新文の成功を返す時点で、変更が保存済みであることを要求する。終了時だけの一括保存にはしない。
- 今回の基本的な完成条件は正常な終了・再オープンとする。書き込み途中のクラッシュからの復旧は後続のWALの段階で扱う。
- 既存ロードマップに沿って、ページ単位のファイル永続化を進める。
- 性能を理想形に近づけるための最適化を先回りして追加しない。

ページ方式の実装順序は [ADR 0001](../adr/0001-phase-implementation-order.md) に記録されている。
今回新たに必要になる判断は、説明・検討を経てからADRに残す。

## 3. 現状と保存対象

現在は `engine.Database.tables` がテーブルを管理し、`engine.Table` が列定義と全行をメモリ上に保持する。
`engine.Execute` がCREATE・INSERT・SELECT・DELETEを実行する。ファイルへの保存は未実装。

| 保存対象 | 例 |
| --- | --- |
| テーブル名 | `users` |
| 列の順序・名前・型 | `id INT, name TEXT` |
| 行データ | `(1, '田中')` |

保存する情報を解釈するため、形式のバージョンやページ・行の位置などの管理情報も必要になる。
管理情報の具体的な項目は今後設計する。

## 4. ファイルとページの意味

DBファイルは、本プログラムが自分たちで定めた形式で読み書きするバイナリファイルである。
テーブル定義や行をバイト列として格納する。

ページは、そのファイル内の固定長の領域である。ページごとにファイルを分けるわけではない。
ページ番号とページサイズから、ファイル内の読み書き位置を計算する。

例えばページサイズが4096バイト、番号が0始まりなら、ページ2の開始位置は8192バイトとなる。
4096バイトという値は現時点では説明用の例であり、具体的なサイズは未確定。

ページ単位にすることで、読み書きと保存領域の管理の単位をそろえられる。
必要な部分だけ読み書きでき、将来のB+木を保存する土台にもなる。
WHEREに合うページが自動的に特定できるわけではなく、インデックスがない検索は基本的に全行走査する。

### バイト列の説明例

`users(id INT, name TEXT)` と行 `(1, '田中')` の情報は、例えば次のように表現できる。
これは各情報の変換例であり、ファイル全体の形式やページ上の配置を定めるものではない。

| 情報 | バイト列（16進数） | 説明 |
| --- | --- | --- |
| テーブル名 | `05 75 73 65 72 73` | 名前のバイト長5とUTF-8の `users` |
| 列数 | `02` | 2列 |
| 列名とINT型 | `02 69 64 01` | 名前のバイト長2、`id`、型番号1 |
| 列名とTEXT型 | `04 6E 61 6D 65 02` | 名前のバイト長4、`name`、型番号2 |
| 整数1 | `00 00 00 00 00 00 00 01` | 8バイトの整数 |
| 文字列「田中」 | `00 00 00 06 E7 94 B0 E4 B8 AD` | UTF-8のバイト長6と本文 |

長さのフィールド幅、型番号、整数のバイト順、上限値は、詳細設計で定める。
Goの構造体のメモリをそのまま保存するのではなく、読み書きで共通の変換規則を使う。

## 5. コンポーネント構成案

以下は今後説明・検討する構成案。パッケージ名や公開APIは未確定。

| 責務 | 担当する内容 |
| --- | --- |
| SQL実行器 | SQLの検証、条件判定、保存操作の呼び出し |
| テーブル管理 | テーブル定義の管理、行の追加・走査・削除 |
| 行とページの形式 | 値とバイト列の相互変換、ページ内の行配置の管理 |
| ページI/O（Pager） | ページの読み書き、新規ページの確保、同期、ファイルのクローズ |

現在の `Table.Rows` をどの段階で置き換えるかは、各責務を説明した後に整理する。
キャッシュやバッファプールの高度な管理は、初期構成に当然必要なものとはしない。

## 6. データフロー案

- DBを開く: ファイルの管理情報を確認し、テーブル定義とデータの場所を取得できる状態にする。
- CREATE: 列定義を検証し、テーブルの定義と管理情報を保存してから成功を返す。
- INSERT: 列数と型を検証し、行をバイト列に変換して保存してから成功を返す。
- SELECT: 保存された行を読み出し、値へ復元し、既存の条件判定と列の選択を適用する。
- DELETE: 条件全体を検証し、一致する行の削除を保存してから成功を返す。
- DBを閉じる: ファイルなどの資源を解放する。更新内容の保存をこの時点まで先送りしない。

同期の方法やI/O失敗後の扱いは未確定。
既存の入力検証エラーでデータを変更しない性質と、書き込み途中のI/O失敗・クラッシュの扱いを分けて設計する。
失敗時のディスクとメモリの状態について、WALなしで保証できる範囲を明記する必要がある。

## 7. 次に理解・検討するテーマ

1. ページの内部構造: 行の位置と長さをどのように管理するか。
2. 行の形式: INT・TEXTの変換規則とサイズ制限。
3. テーブルの管理: 列定義とデータページをどう関連付けるか（カタログ）。
4. ページI/O: ページの読み書き、確保、保存完了の扱い。
5. 実行器との接続: 既存のメモリ管理からの移行と、各SQLの動作。
6. 異常時の扱い: 不正ファイル、書き込み失敗、未対応形式への対応。

これらの説明・検討を経て、必要な詳細設計と実装手順を具体化する。
スロット方式、削除領域の扱い、ページを超える行、キャッシュ方針などの提案は未確定である。

## 8. 実装・検証の進め方（案）

設計が整理できた部分ごとに、次の小さい単位で進める。各段階の具体的なAPIは未確定。

1. ページの書き込みと、ファイルを開き直した後の読み出し。
2. 型付きの値の変換と、ページ内での行の格納・読み出し。
3. テーブル定義の保存・復元。
4. CREATE → INSERT → SELECTと、再オープン後の結果確認。
5. DELETEと、再オープン後も削除結果・列定義が維持されることの確認。
6. 境界値・失敗時の検証と、既存機能の回帰確認。

DB全体がメモリに残っていることで誤って成功しないよう、復元の検証には新しく開いたDBを使う。
クラッシュ復旧の実装は後続のWALの段階で扱う。
