# 永続化の設計

状態: 最初の CREATE → INSERT → SELECT → 閉じる → 開き直す → SELECT に向けた設計。バイト配置などの未確定事項は、対応する部品を作る直前に決めて追記する。

[初期草案](persistence-initial-draft.md)の単一DBファイル案は採用しない。理由は[ADR 0004](../adr/0004-persistence-relations-and-catalogs.md)に記録する。現在の設計と未決事項はこの文書を基準にする。

## 目的と範囲

- テーブル名、列の順序・名前・型、行を保存し、新しく開いたDBから同じSELECT結果を返す。
- 最初は1テーブル・1行を確認する。ページ形式はその後の複数行・複数ページにも使える形にする。
- CREATEとINSERTは必要な書き込み・同期の成功後に成功を返す。入力検証の失敗では保存済みデータを変えない。
- 書き込み途中のクラッシュからの復旧、複数ファイル更新の原子性、同時実行はこの段階の保証に含めない。WALとトランザクションの段階で扱う。

## PostgreSQLから取り入れる構造

PostgreSQLでは通常、テーブルごとにファイルがあり、ファイルは固定長ページの並びになっている。テーブルと列の定義はシステムカタログにあり、カタログ自身もテーブルである。ページ内では項目識別子が行の位置を示す。今回の実装でも、この関係を基本にする。

- [PostgreSQLのファイル構成](https://www.postgresql.org/docs/current/storage-file-layout.html)
- [システムカタログ](https://www.postgresql.org/docs/current/catalogs.html)、[pg_class](https://www.postgresql.org/docs/current/catalog-pg-class.html)、[pg_attribute](https://www.postgresql.org/docs/current/catalog-pg-attribute.html)
- [ページ構成](https://www.postgresql.org/docs/current/storage-page-layout.html)

| PostgreSQLの仕組み | 今回の設計 | 理由 |
| --- | --- | --- |
| テーブルごとのrelationファイル | ユーザーテーブルごとにファイルを持つ | テーブルと保存先の対応を学べる |
| pg_classとpg_attributeなどのシステムカタログ | テーブル情報と列情報を、2つの内部カタログrelationに保存する | 定義もページから復元する構造を学べる |
| 固定長ページと項目識別子 | 8 KiBのページ、ヘッダー、行位置の配列、行本体を使う | PostgreSQLのheapページの基本構造に寄せる |
| WAL、MVCC、空き領域マップ、TOAST、バッファプール | 最初の一連の動作では実装しない | それぞれが必要になった段階で仕組みを調べて追加する |

## ファイル構成とカタログの起動

`OpenDatabase` に渡すパスは、1つのDBのディレクトリとする。最初の構成は次のとおり。

    データディレクトリ/
    ├── CONTROL          形式の識別子、バージョン、ページサイズ
    └── relations/
        ├── 1            テーブル情報の内部カタログ
        ├── 2            列情報の内部カタログ
        └── 3以降        ユーザーテーブルの行

relation番号1と2、およびその列定義は起動のためにコード内で固定する。これらのファイルもユーザーテーブルと同じページI/Oと行配置で読む。PostgreSQLのカタログ起動処理を簡略化し、固定したファイル番号から内部カタログを開く。内部カタログの場所を、そのカタログ自身から探す必要はない。

内部カタログに必要な情報は次のとおり。名称は説明用であり、Goの構造体名や正確なバイト配置ではない。

| 内部カタログ | 1行に保存する情報 |
| --- | --- |
| テーブル情報 | relation ID、テーブル名、行ファイルの番号 |
| 列情報 | relation ID、列番号、列名、内部型 |

テーブル名をファイル名に直接使わず、カタログ上の行ファイル番号からファイルを特定する。relation IDとファイル番号は別の情報として扱う。初版で同じ番号を割り当てても、意味は混同しない。新しい番号は既存カタログを読んで決める。

`OpenDatabase` は、存在しないディレクトリならCONTROLと空の内部カタログを作る。既存ディレクトリならCONTROLを検証してカタログを読み、テーブル名から列定義と行ファイル番号を引ける状態にする。既存ファイルが壊れている場合はエラーを返し、空のDBとして初期化し直さない。行そのものはこの時点で全件読み込まない。

## データページと行

各relationファイルは8 KiBのページを連ねる。ページは少なくとも、版などのヘッダー、行の位置と長さを示す項目識別子、空き領域、行本体を持つ。INSERTは行を格納できるページに項目識別子と行本体を追加する。SELECTはページと項目識別子を走査し、行本体を読む。

行は列定義の順に型付きの値をバイト列にする。INTはint64、TEXTはUTF-8文字列とする。読み出し時は保存した列定義を使って型付きの値へ戻す。エンディアン、長さの幅、ページのヘッダーと項目識別子の正確なバイト配置、1行の最大サイズは、行形式とページ形式の実装直前に仕様として確定する。最初は1ページに収まらない行をエラーにする方針とし、TOAST相当の仕組みは後で検討する。

## 既存の実行器との接続

- `NewDatabase` は従来どおりメモリDBを作る。`OpenDatabase` は永続DBを開く。既存のSQLのASTと `Execute` の呼び出し方は維持する。
- CREATEは型名を変換・検証し、同名テーブルがなければ行ファイルと内部カタログを更新する。保存に成功してからメモリ上のテーブル目録にも反映する。
- INSERTは従来どおり列数と型を全て検証してから、行を符号化し、対象のrelationページへ追加する。
- SELECTは列定義を参照し、永続DBでは対象relationのページを全走査する。読み出した行を既存のWHERE判定と列選択に渡す。メモリDBでは従来のRowsを読む。
- `Close` は開いたファイルを閉じ、エラーを返す。更新時の保存を `Close` まで先送りしない。

CREATEでは行ファイルと複数のカタログファイルを更新する。WALがない段階では、同期しても書き込み途中のクラッシュやI/O失敗で一部だけ残る可能性がある。正常に成功した操作を閉じて開き直すことと、クラッシュ後に整合性を回復することは分けて扱う。PostgreSQLがWALを使う理由もここにある（[WALの概要](https://www.postgresql.org/docs/current/wal-intro.html)）。

## 実装前に確定する詳細

以下は最初の一連の動作に必要だが、部品の実装時に小さく決める。決めた値と読み書きの規則は別の形式仕様書に記録する。

1. CONTROLの識別子とバージョン、および新規作成と既存DBの判別規則。
2. ページヘッダー、項目識別子、空き領域の正確なバイト配置。
3. 内部カタログとユーザー行のINT・TEXTの符号化、サイズ上限。
4. ページの確保と、書き込み・同期の順序。

テストの開閉ヘルパーは、`OpenDatabase` と `Close` ができた段階で実際のAPIに置き換える。設計上の判断を変更する場合は、PostgreSQLの方式、変更理由、このプロジェクトで失う性質をここへ追記する。重要な判断はADRにも記録する。
