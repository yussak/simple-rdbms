# DELETE句の実装方針

現時点では実装前の計画。レキサー → パーサー → 実行器の順に、小さい単位で実装・検証する。

## 対応する振る舞い

- `DELETE FROM テーブル名 [WHERE 条件];` に対応する。セミコロンは省略可能。
- WHERE の省略は全行削除。一致する行がない場合・空テーブルの場合も正常終了する。
- WHERE の比較演算子・AND / OR・括弧・型の規則は [既存のWHERE仕様](../specs/where.md) を引き継ぐ。
- 存在しないテーブルや列、型不一致、不正な条件はエラーにし、既存データを変更しない。
- テーブル定義は保持する。削除後も INSERT / SELECT できる。
- 成功時は INSERT と同様に `nil, nil` を返す。削除件数の返却、RETURNING、USING、ORDER BY、LIMIT は今回扱わない。

## 1. レキサー

- [ ] `TOKEN_DELETE` とキーワード登録を追加する。
- [ ] 大文字・小文字を区別しないことと、DELETE を含む識別子との区別を確認する。

FROM / WHERE と条件に使うトークンは既存実装を使う。

## 2. パーサー

- [ ] `DeleteStatement{Table string, Where Condition}` を追加する。WHERE なしは nil。
- [ ] Parse の分岐と parseDelete を追加する。
- [ ] FROM とテーブル名を読み、WHERE があれば既存の parseOrCondition を使う。
- [ ] 任意のセミコロンの後は EOF を要求する。余分な入力を無視して削除してはならない。
- [ ] WHERE あり・なし、論理条件、不足した FROM / テーブル名 / 条件、不正な文末を検証する。

## 3. 実行器

- [ ] Execute の分岐と executeDelete を追加する。
- [ ] GetTable で対象を取得する。
- [ ] WHERE があれば既存の prepareCondition で条件の木全体を検証する。空テーブルでも省略しない。
- [ ] 元の行を走査し、条件に一致しない行だけを新しい外側スライスに追加する。
- [ ] 最後に一度だけ table.Rows を残す行のスライスへ置き換える。
- [ ] WHERE なしは行を空にし、列定義を保持する。

filterRows は一致した行を取得するための関数なので、DELETE では prepareCondition と matches を直接再利用する。
最初はその場で詰める最適化をせず、元の外側スライスと行の値を変更しない。
これにより、検証エラーによる部分削除を防ぎ、以前の SELECT 結果が共有している外側スライスへの影響も避ける。
永続化・インデックス・トランザクションへの対応は、それぞれを実装する段階で検討する。

## 4. 検証と文書

- [ ] 一部削除・全行一致・一致なし・WHERE なし・空テーブルを検証する。
- [ ] 重複する一致行をすべて削除し、残る行の値と型、列定義を保持することを確認する。
- [ ] テーブル不在・列不在・型不一致を検証する。空テーブルや OR の別条件が真になる場合も検証する。
- [ ] 失敗前後のデータを比較し、一切変更されないことを確認する。
- [ ] CREATE → INSERT → DELETE → SELECT、および削除後の再 INSERT を結合テストで確認する。
- [ ] 既存の SELECT 結果を DELETE が書き換えないことを確認する。
- [ ] 実装に合わせて README、AGENTS.md、docs/todo.md を更新する。
- [ ] go fmt ./...、go test ./...、go build ./...、go vet ./... を実行する。

今回の実行器の中心は「条件全体の検証 → 残す行の収集 → 置き換え」。
条件判定は WHERE で実装済みなので、新しい評価機構を作る必要はない。
